# ADR-009: R14 one-to-one chat data invariants

- Status: Accepted
- Release: R14
- Task: TASK-R14-002
- Change request: CR-0419

## Context

The V042 schema contains the seven planned chat tables, but it cannot prove the
frozen R14 contract. In particular, direct conversations have no canonical
pair key, `client_msg_id` is a nullable bigint while the API uses a non-empty
string, per-user deletion has no explicit representation, and report evidence
is stored as JSON arrays without relational validation.

## Decision

### Direct conversation identity

`conversations.direct_user_low_id` and `direct_user_high_id` store the sorted
member pair. A unique index is the concurrency authority for one conversation
per pair. The columns may be null while a transaction creates the parent before
its members. Triggers on both `conversations` and `conversation_members` are
`DEFERRABLE INITIALLY DEFERRED`; at commit every `DIRECT` conversation must have
exactly two distinct members and a matching non-null canonical pair.

`conversation_members.hidden_at` hides only that member's list view. Deleting a
view must update this column; it must not physically delete a member, message,
receipt, attachment, or the peer's view. `unread_count` is non-null, defaults to
zero, and cannot be negative.

### Message identity, payload, and delivery state

`client_msg_id` is `varchar(64) NOT NULL`, has length 1 through 64, and remains
unique with `sender_id`. The API resource and all four request variants use the
same bounds. Payloads are closed over `TEXT`, `IMAGE`, `CONTENT_CARD`, and
`CONTACT_CARD`; the database validates the matching JSON shape.

Messages start at `SENT`. The complete transition matrix is:

| From | To |
| --- | --- |
| SENT | DELIVERED |
| DELIVERED | READ |

Conversation, sender, payload, type, and client message identity are immutable.
The sender must be a conversation member. The conversation's last-message
pointer must reference the latest message in the same conversation. Image
attachments must reference the payload media, be owned by the sender, and be a
`READY`, non-deleted `private_chat` object. A read receipt belongs to the peer,
the same conversation, and a time no earlier than message creation.

### Report evidence and moderation state

`message_ids` and `evidence_media_ids` remain JSON arrays for compatibility,
but each is a duplicate-free array of at most 100 positive integer strings.
Deferred triggers validate both the report and every related message,
attachment, and media mutation. Message evidence must belong to the reported
conversation. Media evidence must be `READY`, not deleted, in `private_chat` or
`audit_evidence`, and either owned by the reporter or attached to a message in
that conversation. This is the complete, database-verifiable authorization
rule; the schema does not claim an unverifiable direct media-to-conversation FK.

Reports start at `PENDING`, version zero. The complete transition matrix is:

| From | To | Admin decision |
| --- | --- | --- |
| PENDING | APPROVED | APPROVE |
| PENDING | REJECTED | REJECT |
| PENDING | ESCALATED | ESCALATE |
| ESCALATED | APPROVED | APPROVE |
| ESCALATED | REJECTED | REJECT |

Each transition increments `version` by exactly one. Evidence, parties, reason,
and description are immutable after submission.

### Status history

R14 does not introduce a second generic history table or function. Status
changes on `chat_messages` and `chat_reports` invoke the V010 function
`hhy.record_platform_status_history()` and append immutable
`platform.status.changed.v1` facts to `outbox_events` in the same transaction.

## Migration and rollback

V043 locks the affected tables and rejects each ambiguous V042 state before its
first DDL using a distinct `R14_DIRTY_UPGRADE_*` marker. It never invents a
missing client message ID, report reason, or evidence and never merges duplicate
conversations.

U043 is for an empty disposable development/test database only. Any fact in the
seven chat tables raises `R14_U043_BUSINESS_FACTS_PRESENT` before the first DDL.
It never deletes business rows or Outbox history. Production correction is a
new forward migration or an approved backup restore.

## Consequences

- R14 application services must create both members in the conversation
  transaction, use optimistic report versions, and maintain the last-message
  pointer.
- Concurrent direct-conversation creation resolves through the database unique
  pair, not a process-local query-before-insert check.
- The R15 administrator chat-report response currently returns a conversation
  resource instead of report evidence. That separate contract defect is tracked
  in the existing Problem Registry and must be fixed before R15 implementation.
