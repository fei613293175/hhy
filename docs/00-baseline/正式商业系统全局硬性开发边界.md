# 正式商业系统全局硬性开发边界

状态：`FROZEN`
生效日期：2026-07-19
批准变更：CR-0054、CR-0055、CR-0119、CR-0150、CR-0515

本文是跨版本、跨电脑、跨 AI 的强制事实源。聊天记录不能替代本文。

## 1. 用户界面只展示商业信息

- Android、H5、管理端和后续新增前端均不得向用户展示 `requestId`、`traceId`、`challengeId`、nonce、token、fingerprint、Base64、接口名、异常栈、数据库字段或内部状态码。
- 不得展示“敏感信息仅用于本次认证，不会展示或写入日志。”等面向开发或审计的解释性提示。
- 技术信息可以保留在受控日志、诊断对象和服务端链路中，但不得进入正式 UI 组件或页面 DOM。
- 排错期间临时加入的技术信息必须有问题编号，并在问题关闭前移除；回归门禁必须证明正式界面不再展示。
- 用户可见错误只说明发生了什么、用户可以做什么，不泄露内部实现。

## 2. UI 施工必须逐项对齐冻结事实

- 每个页面开发前必须读取页面规格、设计 Token、组件目录、效果图清单和批准的 CR。
- 字号、行高、间距、宽高、圆角、颜色、阴影、遮罩、动画、状态和响应式规则均为硬参数；不得凭感觉替换。
- 效果图不是灵感图，而是页面建模、区域顺序、信息层级、布局、对齐、组件形态、视觉样式和状态关系的强制来源；开发者或 AI 不得自行增加 Hero、卡片、导航、分栏、表单组织或改变组件摆放。
- Design Token、页面规格和组件目录是字号、行高、间距、宽高、圆角、颜色、阴影、遮罩、动画和响应式的强制数值来源。不得从效果图目测数值，也不得用框架默认值替代已登记 Token。
- 完整开发文档、页面字段/状态/动作、API 和批准 CR 是功能、字段、操作、业务状态和正式文案的唯一事实源。效果图中的虚拟功能、无关文字、虚假金额、日期、人数和占位数据不得照搬。
- 删除或替换效果图中的虚拟业务元素必须写入逐页视觉合同；除被明确过滤的元素外，其余建模、布局和视觉样式仍必须还原。若删除后缺少可确定布局，必须先补批准的视觉规格，不得自行重新构图。
- 每个页面必须绑定一个或多个精确面板（例如 `B12/P04`）或一个批准的补充视觉规格。`P01-P08`、`TOKENS_ONLY`、仅参考相邻页面等粗粒度描述不能进入施工；没有精确覆盖就暂停该页面 UI 实现并补规格。
- 页面验收必须同时包含逐页视觉合同、静态参数检查、自动化测试、效果图对照和真机/浏览器截图；只“能运行”不等于 UI 完成。
- 页面还必须通过项目所有者定义的肉眼质量标准：在过滤虚构业务元素后，整体信息密度、层级丰富度、卡片/表单/导航细节、品牌表现和状态完整性仍应接近绑定效果图或批准补充规格的完成度。只满足 Token、字号、边距、圆角、页面身份、接口可用或截图存在，均不得单独判定视觉 `PASS`。
- 禁止为了提高视觉丰富度而虚构关注数、浏览量、评分、金额、标签、头像、图片、按钮、入口或其他业务事实。视觉层级只能由页面合同允许的真实字段、服务端事实、合法占位状态、装饰性非业务资产和已批准组件构成。
- 无直接效果图的页面优先在现有逐页视觉合同中复用相近页面已经批准的视觉语言，并明确来源面板、可复用区域和差异；若无法可靠复用，必须生成效果图补充需求包供项目所有者取得新图，再以批准 CR 纳入同一 UI 规则体系，不得另建并列规则或自行简化交付。
- R02 至 R07 的首次历史视觉回补原计划阻断 R08，CR-0242 已批准先关闭 R08、随后执行全局审计；该历史转换和既有产物不得追溯改写。此例外不允许永久遗留视觉债务：任何历史页面被后续 CR 重新标记为 `IN_REVIEW/BLOCKED` 时，旧 `PASS` 立即失效。
- `catalogs/ui_visual_acceptance.csv` 是逐页视觉验收唯一目录。单版开发检查使用 `scripts/check_ui_visual_acceptance.py --release <版本>`；R12 起机器关闭必须按 `--historical-through <版本>` 的同一实现验证截至当前版本的全部前端页面，任一非 `PASS` 页面均阻断关闭。

### 2.1 视觉与业务冲突裁决

| 内容 | 强制事实源 | 处理方式 |
| --- | --- | --- |
| 页面建模、布局、信息层级、组件形态、对齐与样式 | 精确效果图面板或批准的补充视觉规格 | 必须还原，不允许自行构思 |
| 字号、行高、间距、宽高、圆角、颜色、阴影、动画与响应式 | Design Token、页面规格、组件目录 | 必须使用登记值，不允许框架默认值漂移 |
| 功能、字段、动作、权限、状态机、API | 完整开发文档、合同、批准 CR | 效果图不得新增、删减或改变业务 |
| 正式文案与数据 | 页面规格、文案规则、服务端事实 | 不复制效果图中的虚拟、无关或占位内容 |
| 效果图存在虚拟业务元素 | 逐页视觉合同中的过滤/替换项 | 明确删除或映射真实业务元素，并保持未受影响的视觉结构 |
| 无精确效果图或过滤后布局无法确定 | 批准的补充视觉规格/CR | 先补规格再开发，禁止猜测 |
| 参数与功能均正确但肉眼明显稀疏、粗糙或低于参考完成度 | 效果图/补充规格 + 逐页视觉合同 + 实现截图 | 必须继续优化，不得以“合规基线”判PASS |

### 2.2 成熟客户端架构、图标、导航与动效

- 整体项目必须优先采用大型商业 App 长期验证的官方稳定组件、主流架构和公开维护方案；禁止以省事为由采用小众、预发布或自行构思的基础框架。
- Android 页面导航统一使用稳定版 AndroidX Jetpack Navigation Compose；禁止以页面级 `mutableState`、枚举或自行维护的 List 冒充返回栈，禁止自研导航框架。
- 顶栏返回、系统返回键和手势返回必须操作同一个真实导航栈；返回目标由实际来源决定，不得写死为“首页”“我的”或模块首页。底部导航必须保存所选栏目和各栏目状态；从“我的”进入子页后必须返回“我的”。
- 页面前进、返回和预测性返回统一使用 `HhyMotion` 与冻结 Motion Token；页面不得自行填写动画时长或完全省略导航转场。底部栏目切换使用适合顶层目的地的淡入淡出，不伪装成上下级页面。
- Android 图标只能从 `HhyIcons` 语义注册表引用官方或经批准的矢量资源；禁止汉字、Unicode、Emoji、字体字符和临时文本充当图标。H5、管理端及后续前端同样禁止字符占位图标。
- 上述规则覆盖全部已开发页面和全部后续页面；旧页面发现不符合时必须在当前开发线修复，不能只对新页面生效。
- 官方稳定成熟方案无法满足冻结业务时，必须先以 ADR + 批准 CR 记录差距、选型依据、兼容性、回退和测试；未经批准不得引入替代框架。
- Android 代码变化必须运行 `python scripts/check_android_ui_foundation.py`；门禁失败时不得生成 APK、提交或关闭版本。

## 3. 版本功能不得遗漏

- 每个大版本、任务和 Story 必须逐项核对开发文档、Acceptance Matrix、页面规格、API、数据库和配置清单。
- `合伙云Pro_完整项目开发文档_V1.2_工程执行强化版` 是功能、业务、数据、权限和版本归属的上游基线；实现、补充规格、效果图解释和验收记录必须与其逐项一一对应。补充规格只能细化已登记视觉或施工参数，不得新增、删减、替换或重新组织开发文档明确的功能模块。
- 聚合页面必须承担跨版本回接责任：后续版本完成其列表、详情或发布闭环时，必须同时把开发文档已登记的入口、真实内容卡和真实导航接回对应聚合页面，并在该版本候选中回归；不得以“聚合页属于历史版本”为由遗漏。
- 每个页面或 Story 关闭证据必须能追溯“开发文档章节 → 需求 → 页面/动作/API → 实现 → 测试/截图”。任一环节缺失、使用错误效果图面板或仅以实现自身生成的基线自证，均不得判定完成。
- 未实现、未测试、未追溯、未交付的条目不得标为完成，也不得用后续版本掩盖遗漏。
- 发现旧版本缺口时，以批准热修并入当前开发线；保留原版本追溯，但不得伪造旧产物已包含修复。

## 4. 每个大版本的桌面交付

每个大版本关闭前，除正式 APK 门禁外，还必须在项目所有者桌面生成一份 TXT 或 Markdown 说明，至少包含：

1. 本版实现的全部功能和关键细节；
2. 与开发文档逐项核对的结果；
3. APK 文件名、版本号、Commit 和 SHA-256；
4. 按页面和业务流程编写的详细测试步骤；
5. 预期结果、异常分支和已知限制；
6. 反馈问题时必须提供的截图、操作路径、时间和复现步骤。

缺少该文件、文档一致性核对或桌面 APK 时，大版本不得关闭。

### 4.1 每个大版本的全局漂移审计

R12 起，每个大版本在最终候选完成后、机器关闭和进入下一版之前，必须对以下六项执行一次全局审计：开发文档要求、硬门禁实际执行、开发进度与滚动计划、可复用模式、Problem Registry、踩坑记录。审计报告必须位于仓库、绑定最终候选源码 Commit，并记录报告 SHA-256。

发现规则文本、脚本、工作流、版本状态或经验记录不一致时，必须先检索已有权威规则和 CR，只修订原事实源及其既有投影并补回归；不得新建同义规则，也不得在漂移未清除时关闭大版本。项目所有者真机反馈继续保持异步，不属于该审计的暂停条件。

## 5. 测试能力的生产隔离

- 万能邀请码、测试账号、模拟支付、测试短信等能力默认关闭，只能由显式配置在 DEV、TEST 或 STAGING 启用。
- PROD 必须硬拒绝这些能力；不能仅依赖前端隐藏或口头约定。
- 测试能力的启用环境、用途和撤销方式必须写入版本测试说明，不得把凭据或生产秘密提交到仓库。
- `api.orbexa.cc` 常态必须指向独立的 `owner-test` 持久数据库和非 CI 后端。该库承载项目所有者跨版本真机测试产生的账号、资料、发布内容、会话和配置；版本升级只能替换冻结应用镜像、执行 Flyway 前向迁移并保持同一数据库卷，禁止重建数据库、替换卷、`down -v`、清空用户业务表或把公网入口永久留在版本候选/冒烟库。
- GitHub Actions 候选数据库只能承载自动化夹具并视为可丢弃。候选临时占用公网入口时必须登记最多 45 分钟的路由租约；候选结束无论 PASS、FAIL、取消或基础设施失败，都必须运行同一受控恢复脚本，将公网入口恢复到 `owner-test`，并证明数据库容器、数据卷、非 CI 配置、公开健康和长期测试邀请码连续。
- 每个 Android 大版本 machine-close 前必须运行 `scripts/check_owner_test_environment.py`，并保存服务器侧持久库与公网路由实证。项目所有者没有及时真机反馈不影响继续开发，但不能因此删除、重置或替换其历史测试数据。

## 6. Android 自动化交付硬边界

- R06 起，每个 Android 大版本必须从冻结 Commit 在 `obx-test` 固定工具链完成正式 API、编译、单测、Lint 和 APK 打包，再通过稳定测试签名、版本身份、四方 SHA 与桌面说明门禁后交付 `TEST_APK`。
- 项目所有者真机反馈为异步队列；`owner_physical_test=PENDING` 不阻断桌面测试包先行交付，也不阻断已经完成机器闭环后的顺序推进，但继续阻断该版正式验收和生产激活。
- R14 起每个 Android 大版本机器完成前必须运行一次与该版功能一一对应的 GitHub Actions 固定模拟器候选。旅程必须真实执行点击、输入、长按、返回、重进和关键业务状态断言，并同时审核截图、目标进程日志、JUnit 与机器报告；只看截图、只冷启动或只验证页面存在均不合格。失败不阻断独立合格的 `TEST_APK` 先行交付或异步真机反馈，但必须阻断该版机器完成、生产自动证据和下一业务版本领取。
- 自动修复采用可审计提交和有界三轮重试；同一根因没有新代码或新诊断证据时禁止重跑，禁止 Actions 无审查直接改写生产代码，禁止无限重跑掩盖确定性缺陷。
- 只有在业务测试开始前且日志明确证明为 GitHub、网络、镜像或 Staging 接口瞬态故障（包括 HTTP 5xx）时，才允许同一 Commit 只重跑失败作业及其依赖一次；已经通过的编译、Lint、单测和打包必须复用，不得修改业务代码或重跑全部作业。同一瞬态再次出现时必须停止重跑，转为检查 Staging 健康、服务日志和基础设施。
- 项目所有者真机反馈是异步输入，不要求每个版本在进入下一版本前反馈。任何单版 `owner_physical_test=PENDING` 只阻断该版正式验收和生产激活；R14 起进入下一业务版本仍必须先完成当前版全部 Task、同一冻结 Commit 的 TEST_APK/测试说明/Manifest/Evidence、版本专属交互候选 PASS 和 machine completion PASS，并且只能进入编号紧邻版本。未经明确反馈仍禁止伪造真机 `PASS`。
- `CURRENT_STATUS.yaml`、`NEXT_TASK.yaml` 和现有 Session 只是指针，不得单独作为版本完成事实。R14 起所有 `start`、冷/热 `resume`、`close`、`takeover`、`recover` 必须在任何写入前调用同一仓库证据门禁；缺任务、证据、Release/Commit 身份、候选 PASS、机器完成或出现跳级时必须非零退出且零写入。
- 详细事实源为 `config/android-automation.yaml` 和 `docs/08-testing/Android自动开发测试修复交付体系_V1.0.md`，换电脑、换 AI 不得依赖聊天解释。

### 6.1 GitHub 分层门禁和跨 AI 接续

- 普通提交属于 FAST/MODULE：Android 只执行源码策略、正式 API 地址、编译、单测、Lint 和打包；不得启动模拟器，不得生成候选报告或向项目所有者交付中间 APK。
- 版本候选属于 TEST_APK/RELEASE：只有机器校验通过的 `config/android-candidate-request.yaml` 或默认分支已注册的 `workflow_dispatch(candidate=true)` 才能启动固定模拟器、功能旅程、截图、日志分析和候选报告。
- 开发分支候选入口必须由 `.github/workflows/android-candidate-request.yml` 调用唯一 `.github/workflows/android-quality-gate.yml`，不得复制或削弱候选步骤，不得要求为触发工作流直接修改默认分支。
- Continuity Gate 每次提交必须执行身份、范围、检查点、CR、Trailer 和严格 Doctor；完整临时 Git 生命周期只在连续性核心事实变化时执行。普通业务代码变化不得重复运行完整交接演练，核心事实变化也不得跳过。
- 候选请求、分层策略、失败轮次、机器报告和下一步必须写入仓库与 Context Pack。任何新电脑或新 AI 只凭 `continuity.py resume` 和仓库事实继续，禁止依赖聊天记忆决定测试范围。
