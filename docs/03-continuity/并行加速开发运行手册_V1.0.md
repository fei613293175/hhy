# 合伙云 Pro 并行加速开发运行手册 V1.0

## 1. 目标与边界

本手册落实 `CR-0018`。目标是在不破坏唯一事实源、连续性事件哈希链、资金安全和版本验收的前提下，把开发从横向串行改为纵向 Story 并行。

仓库始终只有一个 ACTIVE 主控 Session。最多 3 个执行代理是该 Session 的受托参与者，不拥有独立 Claim。执行代理的 scratch worktree 不是事实源；只有主控验证补丁并应用到事实分支、完成 Checkpoint 后，变化才算进入项目。

## 2. 角色

| 角色 | 适合模型/推理 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| 主控/架构审查 | 高推理 | 拆 Story、锁路径、CR、架构/资金/状态机审查、集成、Commit、Push、Release | 把重叠写范围同时交给两个代理 |
| 后端与数据执行 | 速度模型中等推理；复杂并发升高 | 迁移、领域服务、OpenAPI实现、模块测试 | 修改客户端、连续性事实、Release事实 |
| 客户端执行 | 速度模型中等推理 | Android/Admin/H5页面、生成类型绑定、模块测试 | 发明字段/按钮、手写重复DTO、修改后端事实 |
| 质量与交付执行 | 速度模型低/中推理；安全审查升高 | 契约、故障注入、测试证据、APK交付验证 | 代替项目所有者确认真机PASS |

模型选择按风险动态调整：页面骨架、CRUD、测试补充和机械同步使用速度模型；资金、状态机、并发、秘密、复杂缺陷和独立审查使用高推理模型。

## 3. 工作区和路径租约

1. 主控在事实分支启动唯一 Session，并完成所需 CR。
2. 主控为每个执行代理创建 detached scratch worktree。
3. 每份委托必须列出唯一 `allowed_paths`；任何未列路径都不可修改。
4. 下列路径仅允许主控修改：`.continuity/**`、`CURRENT_STATUS.yaml`、`NEXT_TASK.yaml`、`releases/**`、`CHANGELOG.md`、CR/ADR、共享锁文件和发布配置。
5. 执行代理不得 Commit、Push、Merge、Tag、部署或上传制品。
6. 执行代理返回：修改文件清单、补丁、MODULE测试命令/结果、风险和未完成项。
7. 主控先检查补丁路径，再应用；发现越界、生成物漂移或测试不完整时整份退回。

## 4. R02 纵向批次

R02 在开发就绪任务后拆为四个并行批次：

- A：Android 启动、登录、邀请注册（STORY-R02-003、004）。
- B：安全会话、冻结、注销（STORY-R02-005、006、007）。
- C：后台用户列表、详情和管控（STORY-R02-001、002）。
- D：H5 邀请注册（STORY-R02-008）。

每批次必须同时包含所需数据迁移、API、客户端、自动化测试和最小可观测性，不允许以“先写完所有后端，再统一补客户端/测试”的方式交付。四批次完成后统一进入 TASK-R02-006 全量集成。

权威口径：本版本实现 19 个新增端点；9 个 Story 集成验证 27 个唯一 operationId，其中 8 个为复用依赖；Release Manifest 共有 25 项权威测试。

## 5. 四级门禁

### FAST

在每次项目变化、Checkpoint 和 Commit 执行。固定校验 Session、Claim、Scope、Secret、CR、Fingerprint、Commit Trailer、事件链及受影响的轻量测试。完整文档 Doctor 仅在文档事实输入变化时加入。

### MODULE

执行代理交付补丁前执行。按影响映射运行后端 Maven 模块、Web 包的 typecheck/test/build、Android unit/lint、契约/数据库专项检查。MODULE 失败的补丁不得交主控。

### INTEGRATION

每天一次或批次汇合时执行：完整后端 verify、确定性生成与漂移检查、Web typecheck/test/build、PostgreSQL 17 迁移与不变量、Android lint/unit/assemble、连续性协议集成。

### RELEASE

在封板前执行 INTEGRATION 全集、Staging/E2E、故障注入、Release Acceptance、APK 构建/签名/四方哈希/HTTPS Range 验证和项目所有者真机验收。

## 6. 生成规则

日常生成只允许确定性、安全的 OpenAPI 类型、领域枚举、页面脚手架、Android派生资产和后端运行时资源。数据库基线重建和 legacy 全契约重建不得进入日常 `generate`。

生成器必须支持只读漂移检查；输入不变时重复运行输出必须字节一致。执行代理不得在页面层手写与生成类型重复的 DTO。

## 7. APK 交付

测试 APK 必须绑定精确 Commit、`versionName`、单调 `versionCode`、稳定测试签名指纹和 SHA-256。固定签名只允许通过 SecretRef/环境注入，不得进入仓库或日志。

交付按两个独立状态推进：

1. `MACHINE_DELIVERY_PASS`：仓库副本、桌面副本、服务器文件和公网 HTTPS 下载四方 SHA/大小一致，签名、包名、API地址和 Range 响应通过。
2. `OWNER_PHYSICAL_TEST_PASS`：项目所有者明确反馈安装、覆盖升级、启动和本批次核心路径通过。

机器验证不能代替真机确认；每个版本 APK 必须保留在电脑桌面供项目所有者测试。

## 8. 集成和停止规则

主控按最小依赖顺序集成补丁，每份补丁集成后运行 FAST；一个批次完整后运行对应 MODULE；每天固定一次 INTEGRATION。小的非阻断 UI 问题可进入后续精修批次，安全、资金、契约漂移、迁移失败和不可安装 APK 必须立即阻断。

每个版本完成 APK 真机验收和 Release Close 后暂停，向项目所有者报告，未经明确指令不进入下一版本。
