# 合伙云 Pro 全项目滚动开发总计划 R02—R32 V1.0

## 1. 结论

本计划以“全项目中粒度 + 当前版本执行级 + 后两版本 Story 级”的滚动方式推进，不在 R02 开发前把 R05—R32 过早拆到代码文件级。

- P00、R01 已完成，规划范围为 R02—R32，共 31 个版本。
- 当前版本 R02 为 `EXECUTION_READY`；R03、R04 为 `STORY_READY`；R05—R32 为 `PORTFOLIO_READY`。
- 实际并发保持 4 槽位：1 个高推理主控 + 最多 3 个隔离执行代理。
- 现行连续性协议只允许 1 个 ACTIVE Session 和 1 个 Task/Story Claim，因此三个执行代理只能在当前 Claim 内按互斥路径并行，不能同时形成三个版本或三个 Task 的事实分支。
- 同一时刻只开发一个业务版本；跨版本只允许只读准备、外部资源准备和风险消除。
- R02—R32 每个版本都必须生成测试 APK，保留桌面副本、完成公网交付校验，并等待项目所有者真机验收。R03 即使没有 Android 页面变化，也必须交付回归 APK。
- R32 的依赖已补齐 R18、R19、R26、R27 旁支，最终生产发布必须传递依赖全部 R02—R31 计划版本。

机器事实源为 `releases/PROGRAM_EXECUTION_PLAN.yaml`，本文件负责解释执行方式。计划由 `scripts/generate_program_execution_plan.py` 确定性生成，并由 `scripts/check_program_execution_plan.py` 阻断漂移、遗漏版本、错误并发和最终依赖不完整。

## 3. 固定执行模型

### 3.1 槽位职责

| 槽位 | 默认职责 | 模型策略 |
|---|---|---|
| 主控 | Session/Claim、CR、架构、共享迁移、资金/安全复核、冲突、集成、提交、推送、APK、Release Gate | 高推理 |
| 执行 A | 后端、数据库、领域不变量、并发、幂等、安全专项 | 复杂模块用高推理 |
| 执行 B | Android、Admin 或 H5；只消费冻结生成类型 | 页面和样板使用快模型 |
| 执行 C | 契约、模块测试、回归、故障注入、生成物漂移、交付预检 | 快模型；高风险安全测试由主控复核 |

执行代理必须使用独立 scratch worktree 和互不重叠的路径租约；不得修改 `.continuity/**`、`CURRENT_STATUS.yaml`、`NEXT_TASK.yaml`、Release 事实或主控共享文件，不得提交、推送、合并和发布。

### 3.2 每版固定流水线

```text
DoR + 唯一 Session/Claim
→ 当前 Claim 内三分区并行
→ FAST / MODULE
→ 主控逐补丁集成
→ INTEGRATION
→ Staging / E2E / 故障注入 / 回滚
→ RELEASE
→ 固定签名 APK
→ 桌面 + 仓库忽略副本 + 服务器 + HTTPS 四方校验
→ 项目所有者真机验收
→ Release 关闭与无状态交接
```

MODULE 由执行代理在其边界内运行；INTEGRATION 在每个纵向切片汇合或每日固定时点运行；RELEASE 只在封板阶段运行。任何资金、状态机、并发、安全、破坏性迁移和签名问题都由主控串行复核。

## 6. 近三版本精细计划

### R02：执行级

- `TASK-R02-002`：Android 启动、登录与邀请注册。
- `TASK-R02-003`：安全会话、冻结与注销。
- `TASK-R02-004`：后台用户列表、详情与管控。
- `TASK-R02-005`：H5 邀请注册。
- `TASK-R02-006`：四批次集成与 25 项权威测试。
- `TASK-R02-007`：固定签名 APK、桌面与公网交付、真机待验收。
- `TASK-R02-008`：关闭与无状态交接。

002—005 是依赖层面的候选集合；现行协议下一次只能领取一个 Task，每个 Task 内再让后端/数据、客户端、质量三个执行代理并行。

### R03：Story级

- `TASK-R03-002 / STORY-R03-001`：短信、R2/OSS、实名供应商版本、连接测试、审批、激活/回滚与 Admin 页面。
- `TASK-R03-003 / STORY-R03-002`：orbexa.cc 域名、DNS 动作、DNS/TLS/服务健康与 Admin 页面。
- `TASK-R03-004 / STORY-R03-003`：支付、出款与证书生命周期配置。
- `TASK-R03-005 / STORY-R03-004`：主控汇合、共享迁移、SecretRef、审批审计、18 项测试与故障注入。
- `TASK-R03-007`：真实外部激活证据与 R03 回归 APK。

R03 的三个业务 Task 仍按唯一 Claim 逐个领取，但 Claim 内使用三个互斥执行分区。共享 API、DTO、迁移编号、路由和生成类型由主控持有。

### R04：Story级

- `TASK-R04-002 / STORY-R04-002`：存储 Scope、R2/OSS、媒体数据不变量、签名 URL、迁移恢复和访问审计。
- `TASK-R04-003 / STORY-R04-001`：创建上传会话、完成上传、私有 readUrl 和删除 API。
- `TASK-R04-004 / STORY-R04-001`：Android 媒体上传管理器、进度、分片重试、取消、预览和删除确认。
- `TASK-R04-005`：存储、API、Android 汇合，6 项测试和供应商故障注入。
- `TASK-R04-007`：R04 APK 桌面、公网和项目所有者真机验收。

R04 私有预览使用冻结响应的 `readUrl`，迁移和审计由内部服务持有。若实现时发现必须新增外部 API，必须暂停并新建 CR。

## 8. 每版 APK 强制规则

每版使用 `versionCode = 10200 + R序号`。机器交付必须先完成固定命令的 Build Evidence，再执行：

1. `prepare`：校验 Release、Commit、versionName/versionCode、固定签名、桌面副本、服务器与 HTTPS 完整下载。
2. `verify`：重复校验四方 SHA-256、大小、MIME 与 Range。
3. `accept`：只在项目所有者明确反馈真机安装、启动和本版本核心路径通过后，将 `owner_physical_test` 从 `PENDING` 单向改为 `PASS`。

模拟器、容器、自动构建和机器安装都不能替代项目所有者真机结论。APK 二进制不提交 Git，但 Manifest 和脱敏证据必须提交。

## 9. 滚动更新规则

每个版本封板时执行一次规划滚动：

1. 用本版本真实周期更新速度基线和风险记录。
2. 将下一版本提升为 `EXECUTION_READY`，拆到代理、路径、页面、接口、数据和测试。
3. 将当前版本之后第三个版本提升为 `STORY_READY`，补齐纵向切片、外部依赖和验收。
4. 重算 DAG、关键路径、READY 队列和最晚外部准备版本。
5. 任何业务范围、页面、API、数据、状态机、资金或配置事实变化都必须另建 CR；不能借规划滚动绕过冻结合同。
6. 计划完成后先暂停，由项目所有者确认后才恢复业务开发。

## 10. 强制验证

```powershell
python scripts/generate_program_execution_plan.py --check
python scripts/check_program_execution_plan.py --json
python -m unittest tests.test_program_execution_plan -v
python scripts/check_v122_documentation.py --strict
python scripts/check_v123_continuity.py --strict
```

验证器至少阻断：版本遗漏、R32 未覆盖全部前序版本、依赖环、错误槽位、多个事实 Session、多个业务版本并行、R02/R03/R04 Story/Task 覆盖不完整、生成计划漂移，以及任一版本缺少 APK 门禁。
