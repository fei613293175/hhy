# 持续开发无状态接续强制门禁 V1.2.3

## 1. 目标与保证边界

目标是让任意 AI、开发者、设备或对话在**仓库记录完整的任何检查点**上恢复工作，不需要旧对话。保证依赖四类证据同时存在：

```text
产品事实
+ 当前任务/会话
+ 文件级WIP指纹
+ Git与验证证据
```

协议不能阻止拥有仓库管理员权限的人蓄意删除 CI、分支保护或历史；这类行为被定义为治理违规。正常受控开发路径中，缺失记录无法 Commit、Push 或 Merge。

## 2. 单一机器状态模型

权威机器状态全部位于 `.continuity/`：

- `CONTINUITY_POLICY.yaml`：唯一机器策略；
- `STATE.yaml`：仓库接续状态；
- `ACTIVE_SESSION.yaml`：当前会话指针；
- `sessions/`：不可覆盖的会话记录；
- `checkpoints/`：文件级恢复检查点；
- `TASK_CLAIMS.yaml`：任务/故事领取；
- `TASK_TRANSITIONS.yaml`：任务迁移账本；
- `CHANGE_REQUEST_INDEX.yaml` 与 `change_requests/`：CR；
- `EVENT_LOG.jsonl`：append-only 哈希事件链。

根 `CONTINUITY_POLICY.yaml` 是指针，`config/CONTINUITY_POLICY.yaml` 是运营视图，二者不能形成第二套机器规则。

## 3. 检查点不只是日志

检查点保存：

- 起始 Commit；
- 变更文件与每个文件的 SHA-256/删除状态；
- 聚合项目指纹；
- 变更分类；
- 测试结果/证据或 NOT_RUN 原因；
- 决策、阻塞和精确下一步；
- 关联 CR；
- Git 状态；
- 事件哈希。

每次检查点同时刷新 Active Pointer 的 Checkpoint ID、项目指纹和租约。因此每个项目 Commit 可以证明自己绑定的是哪个可恢复工作区，而不是只引用一个长期不变的会话编号。

## 4. Commit 与历史验证

每个非合并 Commit 必须绑定一个历史检查点。CI 逐 Commit 加载该 Checkpoint，而不是只看分支最终状态。验证内容包括：

- 主题中的 Task/Story；
- Session、Checkpoint、Tests 和 CR Trailer；
- 该 Commit 的变更文件是否在会话范围；
- 强制记录是否与项目变更同 Commit；
- 测试摘要是否与检查点相同；
- CR 是否与检查点相同；
- Bug、数据库、合同、用户可见变更的伴随证据。

这可以阻止后续 Commit 用一个“最终正确状态”掩盖之前缺少记录的 Commit。

## 5. CR 是完整变更合同

冻结事实变化必须执行：

```text
cr-create → cr-amend → different-actor cr-approve
```

批准前强制存在：原规则、新规则、影响摘要、精确文件、测试、版本、兼容策略和用户确认。仅创建空 CR 编号不能解锁变更。

## 6. 两种交接

### 6.1 进行中 WIP

`handoff` 验证最新检查点与当前文件完全一致，并生成：

- Context Pack；
- Git 状态与日志；
- 二进制 Patch；
- 安全未跟踪文件包；
- Git Bundle；
- SHA-256 Manifest；
- 精确 Takeover 命令。

### 6.2 干净长期交接

`export-clean` 只允许：无活跃会话、工作区干净、Context 最新、事件链有效。它导出完整 Git Bundle、HEAD 源码归档和状态快照。

## 7. 关闭协议

```text
IMPLEMENTATION_CHECKPOINT
→ IMPLEMENTATION_COMMIT
→ CLOSE
→ CLOSURE_CHECKPOINT
→ CLOSURE_METADATA_COMMIT
→ PRE_PUSH / CI
```

关闭元数据包括 Release Task 状态、任务迁移、Changelog、CURRENT_STATUS、NEXT_TASK、Session 和关闭检查点。任何一部分缺失，最后 Commit 或 CI 失败。

## 8. 失败优先原则

当仓库信息矛盾、事件链损坏、Manifest 不匹配、检查点过期或 CR 不完整时，协议必须停止开发并输出明确修复动作。禁止通过询问旧对话“猜回”状态。
